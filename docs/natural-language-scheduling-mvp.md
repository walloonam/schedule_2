# 자연어 일정 추가 MVP 정리

## 1. 목표
- `Home` 화면에서 사용자가 채팅처럼 문장을 입력하면, 시스템이 날짜/시간/제목/우선순위를 해석해 일정 초안을 만든다.
- 첫 단계는 `규칙 기반 파서`로 시작하고, 저장 전에는 반드시 사용자 확인 단계를 둔다.
- 이 문서는 나중에 다시 봐도 이해할 수 있도록 `왜 이렇게 설계하는지`, `어디까지 규칙으로 처리하는지`, `언제 로컬 LLM을 붙이는지`까지 같이 정리한다.

## 2. 왜 규칙 기반으로 먼저 가는가
- 현재 서버 환경에서는 `규칙 기반`이 가장 싸고 안정적이다.
- 일정 파싱은 생각보다 패턴이 반복된다.
- 예시:
  - `내일 오후 3시 회의`
  - `금요일 오전 10시 디자인 리뷰 30분`
  - `오늘 6시까지 긴급 배포 점검`
- 이런 문장은 LLM 없이도 꽤 많이 처리할 수 있다.
- 그래서 MVP는 `규칙 기반으로 최대한 처리 -> 애매하면 확인 요청`이 맞다.

## 3. MVP에서 처리할 입력 범위
### 포함
- 상대 날짜
  - `오늘`, `내일`, `모레`
  - `이번 주 금요일`, `다음 주 화요일`
- 시간 표현
  - `오전 10시`, `오후 3시`
  - `10:30`, `15시`
- 기간 표현
  - `30분`, `1시간`, `2시간`
- 우선순위 표현
  - `긴급`, `중요`, `높음`, `보통`, `낮음`
- 일정 제목 추출
  - 날짜/시간/우선순위를 제거하고 남은 핵심 문구를 제목 후보로 사용

### 제외
- `점심쯤`, `저녁 무렵`, `나중에`, `이번 달 안에`처럼 애매한 시간
- `격주`, `매월 마지막 주`, `공휴일 제외` 같은 고급 반복 표현
- 여러 일정을 한 문장에 동시에 넣는 입력
- 사람 이름, 장소, 외부 캘린더 연동까지 자동 해석하는 기능

## 4. 전체 흐름
1. 사용자가 `Home`에서 자연어 입력창에 문장을 입력한다.
2. 프론트는 `/api/natural-events/parse` 같은 전용 API로 문장을 보낸다.
3. 서버는 규칙 기반 파서로 문장을 해석한다.
4. 결과를 즉시 저장하지 않고, `일정 확인 카드`로 보여준다.
5. 사용자가 확인하면 기존 `/api/events` 저장 흐름을 재사용해 실제 이벤트를 생성한다.
6. 파싱이 실패하거나 정보가 모자라면, 저장 대신 보완 질문 또는 수동 수정 폼으로 전환한다.

## 5. 추천 응답 스키마
```ts
type ParsedScheduleDraft = {
  title: string;
  startAt: string | null;
  endAt: string | null;

  needsConfirmation: boolean;
  missingFields: Array<"title" | "startAt" | "endAt">;
  warnings: string[];
  originalText: string;

```

## 6. 규칙 기반 파서 구조
### 6.1 정규화
- 입력을 먼저 정규화한다.
- 예시:
  - 공백 정리
  - `오후 3시` -> `15시` 계산용 토큰 유지
  - `한시간`, `1 시간`, `1시간` 같은 표현을 동일하게 취급

### 6.2 토큰 추출 순서
- 날짜 먼저
- 시간 다음
- 기간 다음
- 우선순위 다음
- 마지막에 제목 후보 정리

이 순서가 중요한 이유:
- 날짜/시간 표현을 먼저 제거해야 제목이 깔끔해진다.
- 예: `내일 오후 3시 긴급 디자인 리뷰 1시간`
  - 날짜: `내일`
  - 시간: `오후 3시`
  - 우선순위: `긴급`
  - 기간: `1시간`
  - 제목: `디자인 리뷰`

### 6.3 날짜 해석
- 기준 시간은 서버 시간이 아니라 `사용자 로컬 시간대` 기준으로 해석하는 것이 맞다.
- 현재 앱이 단일 사용자 성격이 강하므로, MVP는 서버와 사용자 시간대가 같다는 가정으로 시작해도 된다.
- 구현 시 사용할 수 있는 기준:
  - `오늘`, `내일`, `모레`
  - `이번 주 월요일` ~ `일요일`
  - `다음 주 월요일` ~ `일요일`

### 6.4 시간 해석
- 지원 패턴 예시:
  - `오전 9시`
  - `오후 3시 30분`
  - `15시`
  - `15:30`
- 시간이 하나만 있으면 `startAt`으로 해석하고, 종료 시간은 `duration` 또는 기본 60분으로 계산한다.

### 6.5 기간 해석
- 지원 패턴 예시:
  - `30분`
  - `1시간`
  - `2시간`
- 종료 시간이 없고 기간만 있으면 `startAt + duration`으로 `endAt` 계산
- 종료 시간이 있고 기간도 같이 있으면 우선순위를 정해야 한다.
  - MVP 권장: 종료 시간이 있으면 duration은 경고만 남기고 무시

### 6.6 우선순위 해석
- 현재 앱 태그는 우선순위 용도로 이미 정리돼 있다.
- 매핑 예시:
  - `긴급`, `급한`, `빨리`, `즉시` -> `deadline`
  - `중요`, `높음`, `우선` -> `review`
  - `보통`, `일반` -> `meeting`
  - `낮음`, `나중에` -> `planning`

### 6.7 제목 추출
- 날짜/시간/기간/우선순위 키워드를 제거한 뒤 남은 문장을 제목으로 사용
- 제목이 비면 저장하지 않고 다시 물어본다
- 예:
  - 입력: `내일 3시 긴급`
  - 결과: 제목이 없으므로 실패

## 7. 저장 전 확인 단계가 꼭 필요한 이유
- 규칙 기반은 빠르지만, 사용자의 의도를 100% 맞추진 못한다.
- 특히 이런 경우가 문제다.
  - `금요일`이 이번 주인지 다음 주인지 헷갈리는 경우
  - `3시`가 오전/오후인지 빠진 경우
  - 제목이 너무 짧거나 비는 경우
- 따라서 MVP는 `자동 저장`보다 `확인 후 저장`이 맞다.

추천 UI:
- 사용자 입력: `내일 오후 3시 긴급 디자인 리뷰 1시간`
- 시스템 제안:
  - 제목: 디자인 리뷰
  - 시간: 2026-03-23 15:00 ~ 16:00
  - 우선순위: 긴급
- 버튼:
  - `이대로 저장`
  - `수정 후 저장`

## 8. 실패 케이스와 처리 원칙
### 실패 예시
- `다음주쯤 회의 잡아줘`
- `중요하게 하나 등록`
- `금요일 리뷰`
- `내일 오후에 배포`

### 처리 원칙
- 억지로 저장하지 않는다.
- 모호하면 `부족한 정보`를 명시한다.
- 예:
  - `시작 시간이 애매합니다`
  - `제목이 비어 있습니다`
  - `이번 주 금요일인지 다음 주 금요일인지 확인이 필요합니다`

## 9. 로컬 LLM은 언제 붙이는가
- 규칙 기반에서 실패하는 입력이 누적될 때 붙인다.
- 기준 예시:
  - 실패율이 자주 높을 때
  - 사용자가 자연어를 자유롭게 쓰고 싶어할 때
  - 반복 표현이나 더 긴 문장을 다뤄야 할 때

### 추천 순서
1. 규칙 기반 MVP
2. 실패 로그 수집
3. 실패 유형 분류
4. 정말 필요한 경우에만 로컬 LLM fallback 추가

즉, 처음부터 로컬 LLM을 얹는 것보다 `실패 데이터를 먼저 보는 것`이 훨씬 중요하다.

## 10. 현재 서버 기준 판단
- 현재 서버에서는 규칙 기반 MVP가 가장 적합하다.
- CPU 부담이 거의 없고, Next.js + PostgreSQL과 같이 돌려도 무리가 적다.
- 로컬 LLM CPU 운영은 나중에 검토해도 된다.
- 따라서 지금 스프린트 목표는 `정확한 규칙 설계 + 확인 UI + 저장 흐름 연결`이 맞다.

### 10.1 로컬 LLM 추천 사양
- 규칙 기반을 먼저 쓰고, 실패 케이스만 로컬 LLM으로 보완하는 전제를 둔다.
- 최소 실험용: `4 vCPU / 8GB RAM`
  - 소형 양자화 모델을 시험적으로 돌릴 수 있다.
  - 응답 속도는 다소 느릴 수 있다.
- 권장 실사용: `8 vCPU / 16GB RAM`
  - 규칙 파서 + 로컬 LLM fallback을 함께 운영하기 가장 무난하다.
  - 일정 파싱처럼 짧은 구조화 작업에는 충분히 현실적이다.
- 여유 있는 운영: `16 vCPU / 32GB RAM`
  - 동시 요청이나 더 큰 모델을 고려할 수 있다.
- 결론:
  - `CPU-only 로컬 LLM`은 가능하지만, `규칙 기반 우선 + 애매할 때만 fallback`이 가장 안정적이다.

### Step 5

## 11.1 회귀 테스트 운영
- 자연어 파서는 규칙이 늘어날수록 회귀 테스트가 꼭 필요하다.
- 현재 기준선은 `100개` 케이스다.
- 실행 순서:
  1. `npm run build`
  2. `npm run start`
  3. `npm run test:natural-schedule`
- 테스트 스크립트: [scripts/test-natural-schedule.mjs](/root/schedule_2/scripts/test-natural-schedule.mjs)
- 목적:
  - 지원 범위 안 문장이 계속 잘 파싱되는지 확인
  - 모호한 문장은 계속 안전하게 멈추는지 확인
  - 시간대 처리와 제목 추출이 깨지지 않았는지 확인
- 테스트를 더 늘릴 때는 “정상”, “경고”, “실패” 세 그룹 중 어디에 속하는지 먼저 정하고 추가하는 것이 좋다.

## 12. 공부 포인트
- 정규식만 많이 쓰는 게 핵심이 아니다.
- 더 중요한 건 `해석 순서`, `모호성 처리`, `확인 단계`, `실패 시 안전하게 멈추는 규칙`이다.
- 이 기능은 “잘 맞추는 것”보다 “잘못 저장하지 않는 것”이 더 중요하다.
