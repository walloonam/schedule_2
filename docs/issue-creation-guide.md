# Issue Creation Guide

이 문서는 GitHub issue를 일관된 형식으로 만드는 규칙을 정리한다.
앞으로 새 이슈를 만들 때는 아래 형식을 기본값으로 쓴다.

## 1. 제목 규칙

형식:

```text
[AREA-##] 짧은 작업명
```

예시:

- `[UX-01] Home / Calendar / Briefing 역할 분리`
- `[BE-01] PostgreSQL 저장소 전환`
- `[NLP-01] 자연어 일정 추가 MVP`
- `[QA-01] 자연어 파서 회귀/벤치마크 정리`
- `[OPS-01] 시간대 혼선 수정`
- `[DOC-01] issue log 정리`

## 2. 분류 규칙

라벨과 제목 접두사는 같은 의미로 맞춘다.

- `area:ux` -> `[UX-xx]`
- `area:be` -> `[BE-xx]`
- `area:nlp` -> `[NLP-xx]`
- `area:qa` -> `[QA-xx]`
- `area:ops` -> `[OPS-xx]`
- `area:doc` -> `[DOC-xx]`

## 3. 본문 규칙

본문은 항상 아래 3개 섹션을 사용한다.

```md
## 문제 제기
- 무엇이 불편하거나 부족한지 적는다.

## 해결 방법
- 어떤 방식으로 풀었는지 적는다.

## 결과
- 반영 결과와 남은 후속 작업을 적는다.
```

본문 작성 팁:
- 문제는 사용자 관점으로 적는다.
- 해결 방법은 실제 구현이나 문서 변경 단위를 적는다.
- 결과는 바로 확인 가능한 상태 변화로 적는다.
- 필요하면 관련 파일이나 스프린트 링크를 함께 붙인다.

## 4. 상태 규칙

- 완료된 이슈는 GitHub에서 `closed`로 닫는다.
- 아직 이어서 볼 항목은 `open` 상태로 둔다.
- 완료된 항목은 `docs/issues/issue-log.md`의 `Done`에 동기화한다.

## 5. 생성 순서

1. 제목에 `[AREA-##]`를 붙인다.
2. 적절한 `area:*` 라벨을 붙인다.
3. 본문을 `문제 제기 / 해결 방법 / 결과`로 작성한다.
4. 완료되면 이슈를 닫는다.
5. `docs/issues/issue-log.md`에 반영한다.

## 6. 이번 저장소의 현재 기준

이 저장소에서 현재까지의 주요 영역은 다음과 같다.

- `UX`: 화면 구조, 모달, 정보구조, 사용성
- `BE`: API, PostgreSQL, 저장소, 스키마
- `NLP`: 자연어 일정 파서, 입력 흐름
- `QA`: 회귀 테스트, 벤치마크, 재현 케이스
- `OPS`: 서버/런타임, 시간대, CSS 자산 안정성
- `DOC`: 운영 문서, 스프린트 로그, 인수인계

## 7. 실제 생성 예시

```bash
gh issue create \
  --title "[UX-10] 홈 빠른 입력 개선" \
  --label "area:ux" \
  --body "$(cat <<'EOF'
## 문제 제기
- Home에서 자연어 입력은 가능하지만, 초보자가 어떤 형식으로 써야 하는지 바로 알기 어렵다.

## 해결 방법
- 입력 안내와 예시를 추가하고, 파싱 기준을 문서화한다.

## 결과
- 사용자가 입력 규칙을 바로 보고 따라 쓸 수 있다.
EOF
)"
```

이 저장소에서는 이슈를 만들 때 제목, 라벨, 본문을 같이 맞추는 것을 권장한다.
이렇게 하면 나중에 issue board와 sprint log를 서로 대조하기 쉽다.
